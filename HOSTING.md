# Настоящая админка без обязательных расходов на обучение

## Что теперь есть

Отдельная Django-версия сайта в `server/`. Это реальная общая админка: учётные записи, серверная база SQLite, редактирование меню, загрузка фотографий и сезонные настройки. Сохранённая цена сразу используется и на главной, и в меню. Браузерный черновик не подменяет данные этой версии. Рецептуры и контакты по-прежнему учебные.

Публичный GitHub Pages остаётся бесплатной статической версией и браузерным редактором. Публикация Python-сервера в интернете не выполнялась: у пользователя нет хостинга. Счета, платные услуги и серверы не создавались.

## Самый простой запуск на Windows

1. Скачайте проект целиком и распакуйте ZIP.
2. Если Python ещё нет, установите Python 3.10+ с python.org. При установке включите Python Launcher (`py`).
3. Дважды нажмите `start-windows.bat`.
4. В первый раз дождитесь установки зависимостей и придумайте логин и пароль (минимум 12 символов). При наборе пароля символы не показываются — это нормально.
5. Админка откроется в браузере. Войдите, выберите «Меню», откройте напиток, измените цену и нажмите «Сохранить».
6. Нажмите «Смотреть сайт» в верхней панели админки. Сохранённая цена будет видна посетителю этого сервера.

Для следующих запусков используйте тот же файл; меню и аккаунт сохраняются. Окно терминала нужно оставить открытым. На macOS/Linux команда запуска — `python3 start_cafe.py`.

Это бесплатно и работает на вашем компьютере. Заказчик из другого города по этому локальному адресу войти не сможет. Не открывайте этот сервер наружу через проброс порта: режим разработки не предназначен для этого.

## Права заказчика

Команда `create_customer` создаёт сотрудника с правами на меню и изменение сезона. У него нет доступа к пользователям, группам и системным разрешениям. Восстановление пароля разработчиком: `server/manage.py changepassword ЛОГИН` через тот же виртуальный Python. Для разработчика при необходимости можно отдельно выполнить `createsuperuser`. Готовых паролей в проекте нет.

Фото JPG, PNG и WebP до 5 МБ и 25 мегапикселей проверяются как изображения. Выбранная своя фотография имеет приоритет перед галереей. При удалении фотографии её файл автоматически не удаляется с диска — это защищает от случайной потери; старые файлы может очищать разработчик после резервного копирования.

## Как устроено

Браузер заказчика → вход Django → изменения в базе → публичные страницы читают ту же базу. SQLite и фотографии хранятся в соседней приватной папке `.ilmir-production`, вне сайта. Пользовательские пароли хеширует Django, формы защищены CSRF, есть ограничение повторных неудачных входов в одном процессе. Админка ведёт журнал изменений Django. Изображения выдаются только по случайным именам через отдельный маршрут; база и исходники не публикуются.

`start_cafe.py` создаёт `.cafe-venv`, устанавливает закреплённые зависимости, выполняет миграции и первый импорт меню. Повторный импорт не перезаписывает изменения заказчика. Данные Django не смешиваются с учебным `admin_server.py`.

Сезон: май–сентябрь — лето, октябрь–апрель — осень/зима (Москва). Позиции для каждого сезона готовит человек. Баннер пока общий: для автоматического режима используйте нейтральные заголовок и описание. Сначала загрузите летние позиции, затем включайте лето.

## Если позже нужен публичный сервер

Нужен хостинг с Python либо Docker, HTTPS и **постоянным диском** для SQLite и фото. Бесплатный тариф со стираемым диском не подходит для хранения заказов, меню и загрузок. Тарифы и доступность бесплатных услуг проверяются непосредственно перед выбором; бесплатный постоянный хостинг не обещается. Домен необязателен: сначала можно использовать адрес хостинга.

В проекте есть `server/Dockerfile`. Его нужно собирать из корня репозитория. Постоянный том монтируется в `/data`, доступный пользователю 10001. Обязательные настройки хостинга:

- `DJANGO_SECRET_KEY` — случайный секрет в настройках сервиса, не в Git.
- `DJANGO_ALLOWED_HOSTS` — реальный домен, без схемы.
- `DJANGO_CSRF_TRUSTED_ORIGINS` — `https://ваш-домен`.
- `DJANGO_DEBUG=0`.
- `DJANGO_TRUST_PROXY=1` — только если доверенный HTTPS-прокси перезаписывает `X-Forwarded-Proto`.
- HTTPS до прокси, постоянный диск `/data`, регулярные резервные копии всей папки данных и проверка восстановления.

Production-настройки требуют секрет, включают HTTPS-перенаправление и Secure-cookie. Статические файлы готовятся в сборке через WhiteNoise; SQLite подходит для небольшой кофейни и одного процесса. При росте нагрузки потребуется PostgreSQL, отдельное хранилище фото и общее ограничение попыток входа. В production нельзя использовать `runserver`. Секретные настройки и копии базы нельзя загружать в публичный GitHub.

Контейнерный сценарий подготовлен, но сборка Docker и размещение на хостинге в этой задаче не проверялись. Проверены Django, миграции, импорт, права, изменение данных, публичные страницы и загрузка изображения на текущей машине.

## Проверки

В подготовленном виртуальном окружении:

```sh
DJANGO_DEBUG=1 python server/manage.py test cafe
DJANGO_DEBUG=1 python server/manage.py check
```

На Windows переменная среды устанавливается отдельно через `set DJANGO_DEBUG=1`. Локальная конфигурация нужна только для разработки; для размещения используйте обязательные production-настройки выше.
